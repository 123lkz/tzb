# Agent 1 设计框架文档

> **所属项目**：多源异构数据驱动岗位和能力图谱构建与动态演化分析研究  
> **所属层级**：AI 智能体分析层（紫色层）  
> **核心职责**：新岗位发现 + 能力更新  
> **依赖**：读取 `jobs_clean`，复用 Agent2 的 LLMClient 和 ProfileStore  
> **最后更新**：2026-07-22

---

## 一、设计动机

### 1.1 要解决什么问题

在新一代信息技术领域，岗位和技能处于快速演变中。Agent1 解决两个核心问题：

| 问题 | 现状 | Agent1 的做法 |
|------|------|-------------|
| 岗位目录滞后 | 静态岗位分类无法覆盖新兴岗位 | 从海量招聘数据中自动聚类发现未被收录的新岗位 |
| 技能需求漂移 | 岗位技能需求随时间变化 | 检测同一岗位的技能需求时序变化 |

### 1.2 在整个图谱构建流程中的位置

```
Agent1 负责"发现"——找新东西
Agent2 负责"验证"——确保东西是可信的

Agent1输出 -> MongoDB agent1_output -> Agent2校验 -> jobs_kg -> Neo4j
```

## 三、技术框架

### 3.1 整体架构

Agent 1 采用 Orchestrator + 可插拔模块的架构模式。Agent1Orchestrator 作为主调度器，在初始化时加载三个核心子模块和两个复用模块，运行时按流水线顺序调度。

### 3.2 技术栈

| 层级 | 技术 | 用途 |
|------|------|------|
| 编程语言 | Python 3.12 | 智能体实现语言 |
| 大模型 | DeepSeek Chat（HTTP API）| 新簇智能标注 |
| 向量化 | SentenceTransformer / TF-IDF | 文本语义向量化 |
| 聚类 | HDBSCAN / KMeans | 无监督岗位聚类 |
| 数据建模 | Pydantic v2 | 数据结构定义与校验 |
| 数据库 | MongoDB | 数据持久化 |
| HTTP 客户端 | httpx | LLM API 调用 |
| 日志 | Loguru | 结构化日志记录 |
| 测试 | pytest | 单元测试（95 个）|

### 3.3 模块分解

**新岗位发现模块**：JobClusterer（聚类）-> NoveltyDetector（新兴性检测）-> LabelGenerator（LLM 标注），三条流水线依次执行，每阶段有独立降级方案。

**能力演化检测模块**：SkillTrendAnalyzer（趋势分析）-> EvolutionDetector（演化判定），按岗位分组后做时间窗口聚合和频次统计，判定四种变化类型并检测跨领域迁移。

**输出适配模块**：ChangeRecordBuilder（记录组装）-> GraphInterface（MongoDB 读写），统一包装为 Agent1Output 格式后写入 agent1_output 集合。

### 3.4 数据流设计

`
jobs_clean（输入）
  |
  +-- 左流水线：job_discovery/
  |    读取 title+description+skills -> 文本拼接 -> 向量化 -> 聚类
  |    -> 每个簇 vs nlp_profiles 已有画像 -> 新兴判定
  |    -> DeepSeek 标注 / 统计降级 -> NewPositionSuggestion[]
  |
  +-- 右流水线：skill_evolution/
  |    读取 title+skills+pub_date -> 岗位名归一化 -> 分组
  |    -> 时间窗口聚合 -> 频次趋势计算 -> 演化判定 -> SkillChangeSuggestion[]
  |
  +-- 输出层：output_adapter/
       Agent1Output 统一包装 -> agent1_output（pending）
       -> Agent2 消费校验 -> verified -> merged -> jobs_kg -> Neo4j
`

### 3.5 三阶段独立降级

| 阶段 | 首选方案 | 降级条件 | 降级方案 |
|------|---------|---------|---------|
| 文本向量化 | SentenceTransformer | torch DLL 加载失败 | TF-IDF |
| 聚类 | HDBSCAN | 未安装 hdbscan | KMeans |
| 新簇标注 | DeepSeek LLM | API 网络不通 | 统计规则 |

每阶段独立降级，互不影响。全部降级后流水线仍可完整运行，仅核心职责和典型应用场景输出为空。

### 3.6 API 调用策略

- 调用间隔：每次 LLM 调用前 time.sleep(2)，间隔 2 秒
- 超时控制：HTTP 超时设为 30 秒
- 重试机制：内置 2 次自动重试
- 平滑降级：重试失败后自动降级到统计规则，不中断流水线

### 3.7 与全景图谱的接口

agent1_output 集合中每条记录通过 status 状态机流转：pending -> verified -> rejected -> merged。

全景图谱模块直接查询 status=verified 的记录，Agent2 读取 pending 记录做幻觉防控校验后更新 status，merged 记录最终写入 jobs_kg 进入 Neo4j。

--- 核心字段

| 字段 | 说明 | 来源 |
|------|------|------|
| suggested_name | 岗位名称 | LLM / 统计 |
| core_responsibilities | 核心职责（3-5项）| LLM 生成 |
| suggested_required_skills | 必需技能 | LLM / 统计 |
| suggested_optional_skills | 加分技能 | LLM / 统计 |
| typical_applications | 典型行业应用场景（1-3项）| LLM 生成 |
