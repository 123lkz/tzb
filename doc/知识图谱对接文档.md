# 知识图谱对接文档 — 岗位技能关系数据规范

## 1. 概述

本文档面向知识图谱组，说明岗位与技能之间关系数据的存储方式、字段结构以及如何与系统中其他模块交互。

**项目名称**：新一代信息技术岗位全景图谱 — 人岗匹配平台
**对接系统**：Agent2 关系挖掘引擎 + 人工审核流程
**数据库**：MongoDB（本地实例，默认端口 27017）
**数据库名称**：`recruitment`

---

## 2. 核心集合：jobs_kg（已有的）

`jobs_kg` 是知识图谱组的主要操作对象，存储已审核通过的高质量岗位—技能关系数据。

### 2.1 字段定义

| 字段名 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `_id` | ObjectId | 自动 | MongoDB 自动生成 | — |
| `relation_id` | string | **是** | 关系唯一标识符 | `REL_E67871C176D3` |
| `source_type` | string | **是** | 起点类型（`skill` / `position`） | `skill` |
| `source_id` | string | **是** | 起点实体标识 | `SK_9778840A` |
| `source_name` | string | **是** | 起点名称 | `SQL` |
| `target_type` | string | **是** | 终点类型（`skill` / `position`） | `position` |
| `target_id` | string | **是** | 终点实体标识 | `POS_6C51904D` |
| `target_name` | string | **是** | 终点名称 | `数据分析师` |
| `relation_type` | string | **是** | 关系类型，目前主要为 `requires` | `requires` |
| `confidence` | float | **是** | 置信度评分（`0.0` ~ `1.0`） | `0.887` |
| `explanation` | string | **是** | 自然语言推理过程说明 | `SQL是数据分析师岗位的核心技能……` |
| `source` | string | 是 | 数据来源，主要为 `agent2` | `agent2` |
| `created_at` | string | **是** | 创建时间，ISO8601 格式 | `2026-07-17T15:56:37.002455` |

### 2.2 完整 JSON 示例

```json
{
  "relation_id": "REL_E67871C176D3",
  "source_type": "skill",
  "source_id": "SK_9778840A",
  "source_name": "SQL",
  "target_type": "position",
  "target_id": "POS_6C51904D",
  "target_name": "数据分析师",
  "relation_type": "requires",

```

## 3. 关联集合说明（不用看）

### 3.1 relation_profiles（原始挖掘结果）

存储 Agent2 关系挖掘引擎的直接输出，包含详细的证据、反面证据和推荐类型。

**数据量**：100 条
**与 jobs_kg 的区别**：
- `relation_profiles` 是原始数据，包含 `evidence`、`counter_evidence`、`provenance` 等详细字段
- `jobs_kg` 是简化后的确认数据，仅保留最核心的关系字段

`relation_profiles` 额外字段：

| 字段名 | 类型 | 说明 |
|---|---|---|
| `valid` | bool | 关系是否有效 |
| `evidence` | EvidenceItem[] | 支持证据列表，每项包含 `type`、`detail`、`source` |
| `counter_evidence` | EvidenceItem[] | 反面证据列表 |
| `recommendation` | string | 推荐操作（`strongly_include` / `include` / `exclude`） |
| `provenance` | RelationProvenance | 数据溯源（`created_by`、`created_at`、`llm_model`、`consensus_rounds`） |

### 3.2 audit_queue（待审核队列）

存储低置信度的关系画像，等待人工审核。审核通过后写入 `jobs_kg`，不通过则保留不动。

**数据量**：17 条
**状态字段**：`status` 为 `pending`
**推荐类型**：`exclude`

**内容示例**： `source_name`=渗透测试, `target_name`=产品经理, `confidence`=0.862, `recommendation`=exclude

### 3.3 nlp_profiles（岗位/技能画像）

存储 Agent2 生成的岗位和技能的 NLP 画像。数据分为两类，通过 `type` 字段区分：

**数据量**：61 条（含技能画像和岗位画像）

**技能画像**（`type`=`skill`）：

| 字段名 | 类型 | 说明 |
|---|---|---|
| `skill_id` | string | 技能唯一标识 |
| `name` | string | 技能名称，如 SQL |
| `category` | string | 技能分类 |
| `summary` | string | 自然语言概述（LLM 生成） |
| `prerequisites` | string[] | 前置知识列表 |
| `related_technologies` | string[] | 相关技术栈 |
| `typical_applications` | string[] | 典型应用场景 |
| `proficiency_levels` | object | 熟练度分级（beginner/intermediate/advanced） |
| `industry_trend` | string | 行业趋势 |
| `sources` | string[] | 数据来源列表 |

**岗位画像**（`type`=`position`）：

| 字段名 | 类型 | 说明 |
|---|---|---|
| `position_id` | string | 岗位唯一标识 |
| `name` | string | 岗位名称 |
| `summary` | string | 自然语言概述 |
| `core_responsibilities` | string[] | 核心职责清单 |
| `required_skills` | string[] | 必需技能列表 |
| `optional_skills` | string[] | 加分技能列表 |
| `industry_domain` | string | 所属行业领域 |
| `typical_salary_range` | string | 典型薪资范围 |
| `experience_level` | string | 典型经验要求 |

## 4. 数据流转

以下是岗位—技能关系数据的完整流转过程：

```
jobs_clean (原始岗位数据)
    ↓
Agent2 关系挖掘
    ↓
relation_profiles (100条原始关系，含详细证据)
    ↓ (低置信度的进入)
audit_queue (17条待审核)
    ↓ (人工审核通过)
jobs_kg (23条确认关系)
    ↓
前端知识图谱页面 / 能力洞察页面
```

## 5. 对接要求

### 5.1 知识图谱组需要做的事

1. **读取 `jobs_kg`**：获取已确认的岗位-技能关系数据，用于构建知识图谱。
2. **参考 `nlp_profiles`**：获取岗位和技能的详细画像，用于丰富图谱节点属性。
3. **可选：读取 `relation_profiles`**：获取更丰富的证据信息，用于展示关系的详细说明。

### 5.2 数据维护规范

- `jobs_kg` 中的数据不应被直接删除，如需更新应使用 `update_one` 保留历史记录
- 知识图谱组可以在 `jobs_kg` 中新增自己发现的关系，但建议使用 `source` = `knowledge_graph` 作为标识
- `nlp_profiles` 中的技能和岗位画像是随着新数据动态更新的，不应依赖其息静态内容

### 5.3 扩展接口

当前系统已预留以下扩展点：
- `relation_type` 可扩展为 `depends_on`、`belongs_to` 等关系类型
- 可新增 `graph_embedding` 字段存储知识图谱嵌入向量
- Agent1 的 `agent1_output` 集合中已包含新发现岗位的 payload，可作为知识图谱的节点来源

